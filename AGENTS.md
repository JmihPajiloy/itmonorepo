# itmonorepo

## Назначение и область действия

Это учебный монорепозиторий Университета ИТМО: отдельные задания, лабораторные, решения и отчёты, сгруппированные по дисциплинам. Не считать предметную область одной лабораторной назначением всего проекта. Здесь нет общего сервиса, единой базы данных или обязательного стека.

Эти правила действуют для всего репозитория; особенности задания и локальные инструкции уточняют их в своей папке. Язык документации и отчётов — русский, если задание или пользователь не требуют иного.

## Карта проекта

- `README.md` — обзор и навигация для человека; обновлять при добавлении дисциплин.
- `subjects/<subject>/README.md` — полное название дисциплины и перечень работ.
- `subjects/<subject>/lab<N>/` — самостоятельная лабораторная со всеми её артефактами.
- `subjects/ibbd/lab1` содержит работу по ER-моделированию и 3НФ; `subjects/paszi/lab1` — стенд защиты Parrot OS и отчёт по требованиям АС класса 1В. Каждая работа имеет собственные зависимости и проверки.
- `templates/` — общие помощники и титульные листы для отчётов и других работ.
- `.agents/skills/gost-report/SKILL.md` — процесс создания и изменения Typst-отчётов по ГОСТ. Прочитать при работе с таким отчётом; для обычных SQL-правок или навигации он не нужен.

## Работа с заданием

1. Найти нужную дисциплину и работу, прочитать её `README.md` и исходное задание целиком. Учитывать таблицы и иллюстрации, если они содержат требования.
2. Отличать обязательные требования от примера отчёта. Не переносить чужую предметную область, число таблиц или примеры данных автоматически.
3. Сопоставить требования с существующими результатами и изменить только относящиеся к запросу материалы.
4. Если исходное задание разрешает выбор темы, можно выбрать её самостоятельно. Не утверждать, что тема согласована в таблице потока, без доступа к этой таблице.

Исходные задания сохранять без изменений. Не выдавать синтетические данные, ожидаемый результат или план проверки за реально выполненный эксперимент. Не приписывать прототипу не реализованные ограничения и механизмы доступа.

## Структура и зависимости

- Использовать `subjects/<код дисциплины>/lab<N>`, сохраняя существующие коды и пути.
- Все материалы конкретной работы хранить внутри неё: задание, исходники, отчёт, демонстрационные данные, зависимости решения и результаты проверки. Повторно используемые помощники и титульные листы для отчётов и других работ хранить в `templates/`. Не складывать их в корень.
- Корень предназначен для навигации, общих инструкций и небольших общих команд. Не копировать общие шаблоны в лабораторные. Другой общий код выносить при реальном повторении.
- `README.md` каждой работы должен объяснять, что сделано, где результат, какие зависимости нужны и как воспроизвести работу. Ограничения прототипа указывать явно.
- Для решений локальное Python-окружение — `.venv/` в папке работы. Для Typst-отчётов требуется CLI Typst; не считать установленное окружение частью исходников.
- Сторонние файлы помещать в `vendor/`, сохраняя версии, лицензии и происхождение. Не править код поставщика ради оформления своего отчёта.
- Генерируемые SVG, итоговый PDF и небольшие контрольные результаты можно хранить рядом с исходниками. Окружения исключать из Git. Не исключать все PDF, DOCX или SQLite-файлы глобально: среди них могут быть исходные материалы.
- При переносе файла обновить ссылки, импорты и команды. Не удалять пользовательские данные или настройки IDE под видом уборки; достаточно исключить служебные файлы из Git.

## Команды и проверка

Из корня:

```sh
make check SUBJECT=ibbd LAB=lab1
make report SUBJECT=ibbd LAB=lab1
```

Корневой Makefile передаёт `check` и `report` выбранной работе. При добавлении новой работы подключать только осмысленные для неё цели `check` и `report`; отсутствие такого интерфейса описать в её README.

У ИББД № 1 `check` запускает `verify.py` в БД в памяти и обновляет демонстрационную `lab1.sqlite3`, JSON проверок и CSV. Эта БД воспроизводима; не использовать её для пользовательских рабочих данных. `report` генерирует SVG и запускает CLI Typst; готовый PDF остаётся в корне работы.

Для изменения логики запускать соответствующие содержательные проверки. Для изменения отчёта пересобрать PDF. Правки только README не требуют повторного выполнения всех экспериментов. После переноса файлов проверить именно затронутые пути и команды.

Не записывать успешную проверку, если она не выполнена.

## Границы автоматизации

Не инициализировать Git, не создавать коммиты или удалённые репозитории и не публиковать материалы в рамках обычной работы над лабораторной без соответствующего запроса. На момент создания этих инструкций каталога `.git` нет.

Новые инструкции и навыки должны описывать повторяемые процессы проекта. Не превращать особенности одной лабораторной (например, SQLite, девять таблиц или четыре VIEW) в требования ко всем дисциплинам.
