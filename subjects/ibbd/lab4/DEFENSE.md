# ЛР4: конспект для защиты

## О чём эта лабораторная

ЛР4 — это веб-приложение для базы мастерской. Оно написано на Python с Flask и подключается к PostgreSQL через psycopg 3. Главная идея: приложение не выдаёт себе максимальные права, а входит в БД от имени реального пользователя. Поэтому PostgreSQL сам применяет права, RLS и аудит из ЛР3.

## Короткая речь на 1 минуту

«Я сделал многопользовательский веб-интерфейс к базе `workshop`. Пользователь входит под учётной записью PostgreSQL, и приложение открывает соединение именно от его имени. После входа сервис показывает только доступные по привилегиям таблицы и столбцы, позволяет выполнять разрешённые операции и строит ролевой сводный отчёт. Приёмщик, реставратор и администратор видят разный набор данных. Безопасность не дублируется только в Python: ограничения прав и RLS проверяет сама СУБД, а изменения попадают в журнал ЛР3».

## Что такое веб-сервис в этой работе

Пользователь открывает страницу в браузере. Flask принимает HTTP-запрос, проверяет сеанс и CSRF-токен, затем выполняет запрос к PostgreSQL. Результат превращается в HTML-страницу.

Важно различать роли:

- **браузер** показывает интерфейс;
- **Flask** организует страницы и сеанс;
- **PostgreSQL** хранит данные и окончательно решает, что разрешено пользователю.

## Структура проекта

| Часть | Назначение |
| --- | --- |
| `webapp/auth.py` | Вход, сеансы, CSRF, ограничение неудачных попыток, SCRAM-верификатор |
| `webapp/db.py` | Подключение к БД, список доступных таблиц и столбцов, CRUD-операции |
| `webapp/reports.py` | Сводные отчёты с `GROUP BY` |
| `webapp/__init__.py` | Маршруты Flask и обработка страниц |
| `sql/01_admin.sql` | Роль администратора, RLS-политики и безопасная регистрация пользователей |
| `check.py` | 49 автоматических проверок |

**CRUD** — обычное сокращение: Create (добавить), Read (прочитать), Update (изменить), Delete (удалить).

## Кто что видит

| Учётная запись | Роль | Главная идея доступа |
| --- | --- | --- |
| `reception_orlova` | Приёмщик | Заказчики, инструменты, заказы, оплаты; без удаления |
| `restorer_smirnov`, `restorer_volkova` | Реставратор | Работы и осмотры без контактов заказчика и денежных данных; RLS для своих действий |
| `workshop_admin` | Администратор | Основные данные, журнал и шифртекст секретов; не суперпользователь |

Администратор в приложении — не «всемогущий пользователь PostgreSQL». Ему выданы конкретные права. Например, журнал и зашифрованные секреты он только читает, а не переписывает.

## Почему вход через БД важен

Частая плохая схема: приложение входит в БД одной технической суперролью, а потом само пытается помнить, кому что можно. Если в приложении ошибка, пользователь может получить лишние данные.

Здесь соединение открывается под логином пользователя. Поэтому даже если кто-то вручную сформирует необычный HTTP-запрос, PostgreSQL всё равно применит `GRANT`, столбцовые ограничения и RLS. В журнал изменений попадёт настоящая роль пользователя.

## Безопасность простыми словами

- Пароль не хранится в сессии как открытый текст: в БД используется SCRAM-верификатор.
- Для форм используется **CSRF-токен**. Он защищает от ситуации, когда чужой сайт заставляет уже вошедшего пользователя незаметно отправить запрос.
- После пяти неудачных попыток пара «логин + адрес» временно блокируется в памяти процесса.
- Cookie имеет подпись, чтобы его нельзя было незаметно подменить.
- Список таблиц и столбцов берётся из привилегий базы, а не зашит как список «на глаз».

Ограничение: сервис учебный. Он работает по HTTP на `127.0.0.1`, сессии и счётчики попыток живут только в памяти одного процесса. Для реальной эксплуатации нужны HTTPS, WSGI-сервер, постоянное хранилище сеансов и TLS к БД.

## Сводные отчёты

`GROUP BY` группирует похожие строки, чтобы получить итог. Например, можно сгруппировать оплаты по типу инструмента и посчитать сумму в каждой группе.

Отчёты разные для ролей:

- приёмщик видит оплаты по типам инструментов;
- реставратор — нагрузку по исполнителям и услугам;
- администратор — выработку сотрудников и журнал, сгруппированный по ролям.

Это не просто красивые страницы: запросы показывают агрегацию данных и сохраняют правило минимально необходимого доступа.

## Регистрация пользователей

Администратор использует функцию `app_register_user`. Она выполняется с `SECURITY DEFINER`, проверяет формат логина, разрешённую группу и формат SCRAM-верификатора. Затем создаёт не суперпользователя и, для реставратора, связывает логин с сотрудником.

Функция нужна потому, что обычному администратору приложения не стоит выдавать прямое право произвольно создавать роли в PostgreSQL.

## Что показать на защите

```sh
make venv
make check
make run
```

`make check` пересобирает учебные данные ЛР2–ЛР4 и запускает 49 проверок. `make run` открывает сервис на `http://127.0.0.1:5000`. Можно последовательно показать неудачный вход, экран приёмщика, экран реставратора, RLS и администратора. Готовые снимки лежат в `shots/`.

## Частые вопросы

**Почему нельзя просто скрыть кнопку в интерфейсе?** Скрытая кнопка не является защитой: запрос можно отправить вручную. Настоящее ограничение должно проверяться сервером БД.

**Что делает CSRF-токен?** Доказывает, что запрос на изменение пришёл со страницы, которую отдал наш сервис текущему пользователю.

**Почему RLS всё ещё нужен, если есть роли?** Роль может разрешить работать с таблицей, а RLS ограничивает, какие конкретно строки этой таблицы разрешены.

**Что такое SCRAM?** Механизм проверки пароля, при котором сервер хранит специальный проверочный результат, а не открытый пароль.

**Почему администратор не суперпользователь?** Суперпользователь обходит многие проверки и не подходит для обычной работы через веб-интерфейс.
