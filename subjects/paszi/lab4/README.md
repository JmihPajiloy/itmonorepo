## Быстрый запуск

**На macOS:** откройте папку `subjects/paszi/lab4` в Finder и дважды щёлкните **[start.command](start.command)**. Скрипт при необходимости откроет установленный Docker Desktop, дождётся его готовности, подготовит конфигурацию, поднимет приложение и откроет страницу регистрации в браузере. При первом запуске нужен интернет для загрузки образов и зависимостей. Понадобятся установленный Docker Desktop и Python 3.

Через терминал:

```sh
cd subjects/paszi/lab4
./start.sh
```

Скрипт работает и при вызове по полному пути из другой папки. `./start.sh --no-browser` запускает стенд без открытия браузера. Можно также использовать `make start`.

После появления «Готово!» окно терминала можно закрыть. Остановка — двойным щелчком по **[stop.command](stop.command)** либо командой `./start.sh --stop`. Пользователи и документы сохраняются, повторный запуск открывает ту же БД.

## Запуск через Docker Compose

Требуются Docker Engine с Compose v2+ (или Docker Desktop), Python 3 для создания локальной конфигурации. Node.js и Python для backend на хосте не нужны: приложение собирается внутри контейнеров.

Из папки работы:

```sh
cd subjects/paszi/lab4
python3 scripts/init_env.py
docker compose up --build -d --wait
```

После подготовки `.env` обычный запуск — **`docker compose up`**. Сокращение для первого запуска: `make up`.

Открыть **http://127.0.0.1:8084/register**. Вход: http://127.0.0.1:8084/login.
Новая БД пуста, встроенных учётных записей нет. Пользователи создаются через форму или API.
При первом запуске backend автоматически выполняет `alembic upgrade head`. Готовность БД проверяется до запуска backend, готовность backend — до запуска frontend.

```sh
docker compose ps
docker compose logs backend
docker compose down
```

`down` сохраняет именованный том PostgreSQL. Не добавляйте `-v`, если нужно сохранить созданные данные. Публикуется только frontend на loopback; backend и БД доступны внутри сети Compose.

## Конфигурация

[.env.example](.env.example) содержит имена переменных и учебные образцы. `make env` создаёт `.env` со случайными паролем БД и ключом подписи, правами файла 0600 и никогда не перезаписывает существующий файл. `.env` исключён из Git и архива. При ручном заполнении пароль в DATABASE_URL должен совпадать с POSTGRES_PASSWORD; специальные символы в URL требуют URL-кодирования.

| Переменная | Значение / назначение |
| --- | --- |
| DATABASE_URL | PostgreSQL URL с драйвером psycopg, узел `db` в Compose |
| POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB | Начальная учётная запись и БД контейнера PostgreSQL |
| HASH_SCHEME | `argon2id`; другие алгоритмы конфигурация отклоняет |
| SECRET_KEY | Случайный ключ HS256, минимум 32 символа |
| APP_ENV | `development`, `test` или `production`; само по себе не включает TLS |
| PORT | Внутренний порт backend, по умолчанию 8000 |
| FRONTEND_PORT | Порт на хосте, по умолчанию 8084 |
| ARGON2_TIME_COST | 3 прохода |
| ARGON2_MEMORY_COST | 65536 КиБ |
| ARGON2_PARALLELISM | 4 |
| TOKEN_TTL_MINUTES | 30 минут |

Переменные POSTGRES_* применяются образом PostgreSQL при инициализации нового тома. Изменение `.env` не меняет пароль уже созданной роли в существующей БД.

## Модель доступа

Ресурс имеет неизменяемого через API владельца `resources.owner_id`. Связь `resource_permissions` содержит составной первичный ключ `(user_id, resource_id)` и три независимых флага: `can_read`, `can_update`, `can_delete`.

- Владелец всегда может читать, изменять и удалять свой ресурс, выдавать и отзывать права.
- Другой пользователь выполняет операцию, только если соответствующий флаг установлен.
- Отсутствующая запись или `false` означают запрет.
- Чтение не предоставляет изменение или удаление. Изменение и удаление не предоставляют чтение.
- Даже все три выданных права не позволяют управлять правами других участников.
- PUT полностью заменяет набор прав; пропущенные флаги становятся `false`. DELETE удаляет назначение.
- При каждом запросе backend читает актуальные права из БД, поэтому отзыв действует и для ранее выданного JWT.

Список ресурсов содержит только метаданные собственных объектов и объектов хотя бы с одним выданным правом. Название и ID считаются метаданными; содержимое выдаётся только отдельным GET с проверкой чтения. Прямой запрос известного ID также проходит проверку. Несуществующий ID даёт 404, существующий без права — 403.

## API

JSON передаётся с `Content-Type: application/json`. Для защищённых методов: `Authorization: Bearer <access_token>`.

| Метод | Путь | Назначение и успешный статус |
| --- | --- | --- |
| POST | /api/register | Регистрация `{login, password}`, 201 |
| POST | /api/login | Вход `{login, password}`, JWT и безопасные сведения пользователя, 200 |
| GET | /api/me | Текущая учётная запись, 200 |
| GET | /api/health | Проверка подключения к БД, 200 |
| GET | /api/resources | Список доступных метаданных без содержимого, 200 |
| POST | /api/resources | Создание `{title, content}`, владелец определяется из JWT, 201 |
| GET | /api/resources/{id} | Чтение с `can_read`, 200 |
| PATCH | /api/resources/{id} | Замена `{title, content}` с `can_update`, 200 |
| DELETE | /api/resources/{id} | Удаление с `can_delete`, 204 |
| GET | /api/resources/{id}/permissions | Список назначений; только владелец, 200 |
| PUT | /api/resources/{id}/permissions/{login} | Выдача/замена `{can_read, can_update, can_delete}`; только владелец, 200 |
| DELETE | /api/resources/{id}/permissions/{login} | Отзыв назначения; только владелец, 204 |

Ответ ошибки содержит `message`. Статусы: 422 — валидация, 409 — занятый логин или назначение самому владельцу, 401 — нет действительного сеанса, 403 — нет права, 404 — ресурс или получатель отсутствует, 503 — ошибка обращения к БД.

Логин: 3–32 символа из `A-Z a-z 0-9 . _ -`, регистр значим. Пароль: 8–128 символов, заглавная и строчная латинские буквы, цифра, хотя бы один ASCII-знак пунктуации (включая `_`). Название ресурса: 1–100 символов, содержимое: 1–10000; строки из пробелов отклоняются. Неописанные поля, включая попытку передать `owner_id`, отклоняются.

### curl: владелец, получатель и посторонний

Команды рассчитаны на новую БД и используют **публичный учебный пароль**, а не локальные секреты. Для извлечения значений нужен Python 3. В повторном запуске используйте новые логины либо войдите в существующие записи.

```sh
BASE=http://127.0.0.1:8084
for LOGIN in owner reader outsider; do
  curl -sS "$BASE/api/register" -H 'Content-Type: application/json' \
    -d "{\"login\":\"$LOGIN\",\"password\":\"Lab4-DemoPass1!\"}"
done

OWNER_TOKEN=$(curl -sS "$BASE/api/login" -H 'Content-Type: application/json' \
  -d '{"login":"owner","password":"Lab4-DemoPass1!"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')
READER_TOKEN=$(curl -sS "$BASE/api/login" -H 'Content-Type: application/json' \
  -d '{"login":"reader","password":"Lab4-DemoPass1!"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')
OUTSIDER_TOKEN=$(curl -sS "$BASE/api/login" -H 'Content-Type: application/json' \
  -d '{"login":"outsider","password":"Lab4-DemoPass1!"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')

RESOURCE_ID=$(curl -sS "$BASE/api/resources" \
  -H "Authorization: Bearer $OWNER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"title":"План работы","content":"Вариант 2"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["id"])')

curl -i -X PUT "$BASE/api/resources/$RESOURCE_ID/permissions/reader" \
  -H "Authorization: Bearer $OWNER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"can_read":true,"can_update":false,"can_delete":false}'
# 200: получатель читает; 403: посторонний не читает
curl -i "$BASE/api/resources/$RESOURCE_ID" -H "Authorization: Bearer $READER_TOKEN"
curl -i "$BASE/api/resources/$RESOURCE_ID" -H "Authorization: Bearer $OUTSIDER_TOKEN"
# 403: одного чтения недостаточно для изменения
curl -i -X PATCH "$BASE/api/resources/$RESOURCE_ID" \
  -H "Authorization: Bearer $READER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"title":"Изменение","content":"Новая версия"}'
# 204: отзыв; затем 403 с тем же токеном получателя
curl -i -X DELETE "$BASE/api/resources/$RESOURCE_ID/permissions/reader" \
  -H "Authorization: Bearer $OWNER_TOKEN"
curl -i "$BASE/api/resources/$RESOURCE_ID" -H "Authorization: Bearer $READER_TOKEN"
```

## Проверки и демонстрация через UI

```sh
make check                       # pytest в отдельной случайной схеме PostgreSQL
```

Из корня монорепозитория: `make check SUBJECT=paszi LAB=lab4`.
Тесты применяют настоящие миграции, проверяют совпадение ORM и схемы, выполняют откат и повторное применение миграции. Данные приложения не очищаются: после тестов удаляется только созданная тестовая схема. Для её создания требуется право CREATE на текущую БД.

Проверяются регистрация и хэш с солью, валидация, конфликт и гонка логинов, вход и JWT, разрешённые/запрещённые операции, независимость прав, выдача только владельцем, отзыв, каскадное удаление и отсутствие секретов в логах. Фактическое число проверок хранится в JUnit XML и [summary.json](verification/summary.json).

Вручную: зарегистрировать три учётные записи; войти владельцем, создать документ, ввести логин напарника и выдать только чтение. Выйти и войти напарником, открыть документ и попытаться сохранить изменение. Под третьим пользователем ввести известный ID и нажать «Прочитать». Отозвать право владельцем и повторить чтение напарником. Сеансы разных пользователей удобно держать в разных вкладках: токен хранится в памяти конкретной вкладки.

Для повторения автоматической проверки интерфейса нужны Node.js 22.16+ и установленный Google Chrome:

```sh
cd frontend
npm ci
npm run build
npm run shots
```

Сценарий создаёт три новые учебные записи с уникальными логинами, сохраняет статусы HTTP, проверяет содержимое и отказ после отзыва, отсутствие ошибок браузера и горизонтальной прокрутки на экране 390 px. Затем восстанавливает право чтения для демонстрации. Последние логины и ID — в `verification/ui.json`, пароль этих **тестовых** записей — `Lab4-DemoPass1!`. Скрипт не удаляет ранее созданные записи. Крупные снимки 12–16 сняты непосредственно с элементов/областей интерфейса для читаемости отчёта. Снимок 11 — настоящее меню веток WebStorm; текущая ветка `main`, Git не изменялся.

## Безопасность: что сделано

- Argon2id, отдельная случайная соль 16 байт на пароль, хэш 32 байта, параметры из конфигурации. В БД сохраняется только кодированная строка хэша.
- Уникальное ограничение PostgreSQL на логин; перехват конфликта после INSERT обеспечивает 409 и при одновременной регистрации.
- Серверная валидация и запрет лишних полей; пароль представлен SecretStr. Ответ 422 не содержит исходный `input` Pydantic.
- Аутентификация по подписанному JWT HS256 с обязательными sub/iat/exp, issuer и audience; срок действия 30 минут. Поддельный и истёкший токены отклоняются.
- Пароли, хэши, JWT, заголовки и тела запросов не логируются. События приложения — JSON с INFO/ERROR. Ошибка БД возвращается без текста SQL и параметров.
- Все операции с ресурсами проверяются на backend; владельца нельзя передать/изменить через API. Права не копируются в JWT.
- Запросы ORM параметризованы. Первичные и внешние ключи защищают целостность назначений; удаление ресурса удаляет его права.
- Токен находится в памяти вкладки, без localStorage, cookie и передачи через URL. React выводит пользовательский текст без HTML-интерпретации; Nginx добавляет CSP и nosniff.
- Backend запускается непривилегированным пользователем контейнера. БД и backend не публикуют порт на хост; frontend слушает только 127.0.0.1.

### Ограничения учебного прототипа

Локальный запуск использует HTTP; для сетевого развёртывания нужны HTTPS и отдельная конфигурация доступа. Нет подтверждения почты, восстановления/смены пароля, MFA, ограничения частоты запросов, пагинации, защиты от перебора и централизованного неизменяемого аудита. Начальная роль PostgreSQL, создаваемая официальным образом, имеет административные права: для эксплуатации её нужно разделить с ролью приложения.

Выход удаляет токен из вкладки, но серверного списка отозванных JWT нет: скопированный JWT действителен до истечения срока. Перезагрузка страницы требует нового входа. Отзыв права запрещает следующие запросы, но не стирает уже прочитанную копию из памяти пользователя. Пользователь с правом удаления может окончательно удалить ресурс; UI запрашивает подтверждение, а API выполняет авторизованный DELETE напрямую. Управление владельцем и передача права дальнейшего делегирования не реализованы.
