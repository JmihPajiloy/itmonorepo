# Лабораторная работа № 5 по ИББД

Шибаев Иван Дмитриевич, Малышев Григорий Игоревич, N3352.
Тема: «Резервирование БД и восстановление по контрольным точкам».
База данных — `workshop` из [ЛР2](../lab2/README.md) с журналом, шифрованием и ролями
[ЛР3](../lab3/README.md) (PostgreSQL 14).

## Что сделано

1. Стратегия резервирования: ежедневная физическая базовая копия (`pg_basebackup`, проверка
   `pg_verifybackup`) + непрерывное архивирование WAL (`archive_command`, `archive_timeout = 300`)
   для восстановления на любой момент (PITR) + ежедневная логическая копия `pg_dump -Fc` и ролей
   (`pg_dumpall --globals-only`); хранение `KEEP` последних копий (по умолчанию 7) и очистка
   архива WAL `pg_archivecleanup`.
2. Контрольная точка — именованная точка восстановления `pg_create_restore_point('lab5_before_changes')`
   после базовой копии; затем случайные изменения (воспроизводимые через `setseed`) от имени
   `postgres` и `reception_orlova` в 6 таблицах.
3. Откат: остановка сервера, перенос каталога данных в `work/pgdata.before-restore`, восстановление
   базовой копии и WAL до точки `lab5_before_changes` (`recovery_target_name`), переход на линию
   времени 2. Проверка: число строк и MD5 содержимого 9 таблиц и журнала совпадают с состоянием до
   изменений; логическая копия тоже восстанавливается в отдельную БД и совпадает.
4. Анализ откаченных изменений: журнал ЛР3 откатывается вместе с БД; `pg_waldump` по архиву WAL
   показывает записи Heap по таблицам и транзакции после точки восстановления; вторая копия,
   восстановленная до конца WAL линии времени 1 (порт 55434), содержит изменённые данные и записи
   журнала ЛР3 (кто, когда, что было и стало); журнал сервера (`log_statement = 'mod'`) хранит
   тексты операторов.

## Команды

```sh
make check SUBJECT=ibbd LAB=lab5   # из корня; или make check в папке работы
make report SUBJECT=ibbd LAB=lab5
```

`check.sh` удаляет и заново создаёт `work/`, поднимает собственный кластер на 127.0.0.1:55433
(общий кластер 55432 не затрагивается), строит БД сценарием ЛР3 (`IBBD_OUT` — во временный каталог),
а в конце останавливает кластеры на 55433 и 55434. Данные в `work/` остаются для просмотра:
`work/pgdata` — восстановленный кластер, `work/pgdata.before-restore` — каталог до отката,
`work/pitr-latest` — копия на момент до отката, `work/backups`, `work/wal_archive`, `work/waldump.txt`.

Ручной запуск задания и восстановление:

```sh
IBBD_PGDATA="$PWD/work/pgdata" IBBD_PGPORT=55433 ../tools/pg.sh start
KEEP=7 ./backup.sh
./restore.sh work/backups/<время>/data work/new-pgdata lab5_before_changes
```

Переменные `backup.sh`: `IBBD_PGPORT` (55433), `BACKUP_ROOT` (`work/backups`),
`WAL_ARCHIVE` (`work/wal_archive`), `KEEP` (7).

## Границы результата

- Расписание описано в `crontab.example`, но в crontab/launchd не устанавливалось: в `check.sh`
  задание `backup.sh` запускается вручную два раза подряд с `KEEP=1`, чтобы показать ротацию.
- Копии и архив WAL лежат на том же диске, что и кластер, и не зашифрованы (защищены только
  правами 0700/0600). Для реального использования нужны внешнее хранилище и шифрование.
- `archive_wal.sh` копирует сегменты через `cp` без `fsync`.
- Точное время восстановления не измерялось отдельно; оценка — по отметкам времени журнала сервера.
- `pg_waldump` показывает таблицы, операции и транзакции, но не значения полей; значения получены
  из копии, восстановленной до конца WAL.
- Суперпользователь `postgres` учебного кластера входит без пароля с 127.0.0.1 (как в ЛР2–ЛР3).
