# ЛР2: конспект для защиты

## О чём эта лабораторная

В ЛР1 была спроектирована модель. Здесь она реализована в настоящей серверной СУБД PostgreSQL 14: созданы таблицы, связи, ограничения, индексы, демонстрационные данные и представления.

## Короткая речь на 1 минуту

«В этой работе я перенёс модель мастерской из ЛР1 в PostgreSQL. Таблицы создаются отдельным скриптом, затем через внешние ключи задаются связи, после этого создаются индексы и добавляется поле даты закрытия заказа. В таблицы загружены демонстрационные данные. Также перенесены четыре представления для приёмщика и реставратора. Проверочный сценарий пересоздаёт базу и фиксирует структуру, ограничения, индексы и результаты запросов».

## Что такое PostgreSQL и SQL

**PostgreSQL** — серверная система управления базами данных. В отличие от SQLite из ЛР1, она работает как отдельный сервер, поддерживает учётные записи, права доступа, журналирование и восстановление.

**SQL** — язык команд для работы с базой. Самые нужные слова:

- `CREATE TABLE` — создать таблицу;
- `INSERT` — добавить строку;
- `SELECT` — прочитать данные;
- `ALTER TABLE` — изменить уже созданную таблицу;
- `CREATE INDEX` — создать индекс;
- `CREATE VIEW` — создать представление.

## Как устроена реализация

Скрипты применяются в логическом порядке:

1. `01_tables.sql` — девять таблиц и базовые ограничения.
2. `02_relations.sql` — внешние ключи между таблицами.
3. `03_indexes.sql` — индексы для связей и поиска.
4. `04_alter.sql` — изменение структуры: поле `closed_on` в заказе.
5. `05_data.sql` — по восемь и более демонстрационных строк в основных таблицах.
6. `06_views.sql` — четыре представления из ЛР1.

Такое деление полезно для защиты: видно, что таблица, связь, индекс и изменение схемы — разные операции.

## Ключи и связи

Первичный ключ — уникальный идентификатор строки, например `order_id` для заказа. В PostgreSQL для большинства таких полей используется `GENERATED BY DEFAULT AS IDENTITY`: сервер сам может выдать новый номер.

Внешние ключи заданы отдельно через `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY`. Например, `restoration_order.instrument_id` ссылается на инструмент. `ON DELETE RESTRICT` запрещает удалить родительскую строку, если она ещё используется.

## Ограничения целостности

Это правила, которые проверяет сервер:

- `NOT NULL` — значение обязательно;
- `UNIQUE` — повторов быть не должно, например у инвентарного номера;
- `CHECK` — логическое правило, например положительная оплата;
- `FOREIGN KEY` — ссылка должна вести на существующую строку.

В заказе дополнительно проверяется, что срок готовности не раньше даты приёма. Частичный уникальный индекс запрещает два активных заказа на один инструмент: уникальность действует только для состояний `accepted`, `in_progress`, `ready`.

## Зачем нужны индексы

Индекс — вспомогательная структура, ускоряющая поиск. Это похоже на алфавитный указатель в книге: он занимает место и немного замедляет изменение данных, но ускоряет поиск.

В этой работе индексы есть на внешних ключах и частых условиях поиска: ФИО и телефоне заказчика, состоянии и сроке заказа, состоянии работы, дате осмотра и дате оплаты.

PostgreSQL не создаёт индексы для внешних ключей автоматически. Поэтому они добавлены явно. Это важно при соединениях таблиц и при проверке удаления родительских строк.

## Что показало изменение структуры

В `04_alter.sql` к заказу добавляется `closed_on` — дата фактического закрытия. Это демонстрирует, что готовую схему можно развивать без создания базы заново. Поле проверяет согласованность с датой приёма и состоянием заказа.

## Представления

Сделаны те же четыре VIEW, что и в ЛР1:

- два для приёмщика: реестр заказов и финансовая сводка;
- два для реставратора: очередь работ и история осмотров.

VIEW не дублирует данные. Оно выполняет сохранённый запрос и показывает удобный срез нескольких таблиц. Права на эти VIEW появятся в ЛР3.

## Частые вопросы

**Чем PostgreSQL лучше SQLite здесь?** PostgreSQL — многопользовательский сервер, у него есть роли, права, RLS, архивирование WAL и PITR. Всё это понадобится в следующих работах.

**Почему связи не записаны просто числами без FK?** Число без внешнего ключа может указывать на несуществующую запись. FK не даёт создать такую ошибку.

**Почему не создать индекс на каждом столбце?** Каждый индекс занимает место и удорожает `INSERT`, `UPDATE`, `DELETE`. Индексируют поля соединений, поиска и сортировки, а не всё подряд.

**Что значит частичный уникальный индекс?** Он проверяет уникальность не для всех строк, а только для строк, подходящих под условие. Здесь условие — активное состояние заказа.

**Что такое транзакция?** Группа операций, которая выполняется целиком или не выполняется вообще. Скрипты обёрнуты в `BEGIN` и `COMMIT`, чтобы не осталась половина схемы при ошибке.
